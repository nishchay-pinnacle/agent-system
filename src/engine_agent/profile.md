# Fortanix — Confidential Computing Manager (CCM)

## What it is and why it matters
**CCM is the control plane for deploying, verifying, and managing confidential-computing workloads.** It manages applications, builds, node enrollment, attestation, workload identity/certificates, policies, and workflows rather than supplying processor isolation itself. Hardware Trusted Execution Environments (TEEs) provide isolation; CCM verifies evidence and decides which approved workloads receive credentials or access to protected material. Current positioning emphasizes confidential CPU/GPU infrastructure and sensitive AI, but documentation and customer evidence also cover conventional applications and private data collaboration. It is available as SaaS and on-premises. [S2][S3][S5][S8][S11]

The customer problem has two layers:
- **Runtime trust:** encryption at rest and TLS leave data decrypted during processing. Enterprises may not want cloud administrators, host operators, hypervisors, or compromised infrastructure to see patient data, business information, model weights, or proprietary code. This can block cloud migration, sensitive AI use, and collaboration. [S1][S3][S17]
- **Operational fragmentation:** independently managed confidential-computing components create separate configuration, verification, monitoring, and policy work. CCM proposes one control plane and composite CPU/GPU attestation before sensitive assets become available. Simplified operation and performance at scale are vendor claims, not measured results in the reviewed evidence. [S2]

The intended change is from **trusting infrastructure and stitching together controls** to **approving workloads, verifying their execution environment, and conditioning credentials/key access on verification**. It adds operational and trust machinery; it does not replace every application security control. [S3][S7][S12]

## Boundaries within Fortanix
- **CCM:** confidential infrastructure/application management, attestation verification, approved workload identity and certificates, policy checks, monitoring, and orchestration. On-premises architecture also describes releasing configured secrets. [S8][S11]
- **Data Security Manager (DSM):** the HSM/KMS and cryptographic-services component in the documented joint secure-key-release design. DSM validates CCM-issued certificates before releasing cryptographic material. DSM's stated FIPS 140-2 Level 3 status is not certification of every CCM workload or an automatic compliance guarantee. [S3]
- **Confidential AI:** the broader Fortanix/NVIDIA solution combining confidential CPUs/GPUs, attestation, and gated access to data/model keys. It includes VM and Kubernetes Confidential Containers (CoCo) paths. CCM is an enabling control-plane component, not synonymous with every capability or customer result of the broader solution. Some sources retain the Armet AI name. [S3][S6]
- **Armor/platform context:** current quickstart accesses CCM through a Fortanix Armor account and IAM groups. Support also maintains a separate `ccm.fortanix.com` documentation tree. Older CCM 3.0 material is SGX/SaaS-oriented and should not override current deployment-specific availability. Exact commercial bundling, universal DSM requirements, and supported third-party key-release substitutes remain unresolved through public research (Q8). [S9][S11][S15][S16]

## Who needs it, and when
**Supported customer situations:**
1. **Sensitive AI/RAG:** encrypted documents, embeddings, vector databases and model weights must be processed on verified CPU/GPU environments. CCM attestation and DSM key release provide an access gate before decryption. [S3]
2. **Model-IP distribution:** model owners want enterprise customers to run proprietary models near their own data without giving infrastructure operators access to weights. Confidential AI statements from ElevenLabs, Resemble AI and Deepgram illustrate this broader solution need, not isolated CCM performance. [S6]
3. **Private multiparty collaboration:** organizations want algorithms to access sensitive data without disclosing source data or algorithm IP to other parties. The healthcare exchange case explicitly names CCM; BeeKeeperAI describes this problem with Fortanix confidential computing and DSM. [S5][S17]
4. **Conventional sensitive applications and sovereign cloud:** business logic, transaction processing, tokenization, signing, and multitenant SaaS can use attested identities and policy-gated keys instead of assuming third-party infrastructure is trustworthy. These are vendor-described use cases, not all demonstrated customer deployments. [S3]

**Fit inference:** strongest where infrastructure-operator trust, data/model confidentiality, sovereignty, or multiparty access is a material blocker, and teams can adopt compatible confidential hardware plus workload/credential policies. Less compelling if the only requirement is storage encryption or the workload cannot move to a supported TEE; this is qualification reasoning, not a vendor exclusion rule. No minimum company size or economic break-even scale was established. [S2][S3][S10][S11]

**People:** documented work involves account/IAM administrators, node/infrastructure operators, application-build creators, and managers approving builds and certificate domains. Platform/security teams are inferred operating groups; AI/application developers, model owners and data stewards are likely beneficiaries. Healthcare data stewards specifically must permit access while protecting patient information. These do not establish the economic buyer or procurement approval chain (Q4). [S11][S12][S17]

## How it works in practice
### Deployment and application lifecycle
The Armor quickstart sequence is: obtain platform/account access → create IAM group → add application/platform type → create a platform-specific build → approve/allowlist build → enroll compute infrastructure/node agent → run the approved build. The illustrated Enclave OS path uses a converted Docker image and private registry; VM, EDP, ACI and CoCo paths differ. The quickstart lists Azure access yet demonstrates AWS Nitro, so its prerequisites should not be generalized universally. [S11]

A customer-side **Node Agent** collects attestation evidence, enrolls infrastructure and proxies application certificate requests. The backend manages applications, configurations and policy and verifies evidence through Azure MAA, AMD KDS, NVIDIA NRAS and Intel-related PCCS/PCS. The described on-prem backend runs inside an SGX enclave with an encrypted metadata datastore. Its architecture lists some fixed external attestation endpoints; air-gapped suitability should not be inferred from platform-wide marketing. [S8]

Users allowlist enclaves through UI/APIs. Applications obtain attested TLS identities; Enclave OS can automate certificate requests through manifest settings. Optional enclave-signed heartbeats support monitoring. Node provisioning is described as once per node-agent-process lifecycle; heartbeats are not proof of continuous re-attestation. [S7]

### Composite attestation and key access
The joint architecture blog describes:
1. CPU attestation of measured state, firmware and launch policy through relevant vendor services.
2. GPU evidence verified through NVIDIA NRAS; CCM validates CPU/GPU evidence and creates a unified composite identity/certificate.
3. Workload key pair/CSR enrollment; expected metadata and policies such as region, workload and tenant are checked before a Zone-CA-signed X.509 certificate is issued.
4. Application authenticates to DSM over mTLS using the CCM-issued certificate. DSM validates the trusted issuer before releasing database keys, model decryption keys, tokens or other material into the attested context.
5. Attestation, certificate issuance and key-release events are logged. Claims of immutable/regulator-ready evidence and end-to-end confidentiality are vendor descriptions, not independently assessed here. [S3]

Thus CCM is more than a dashboard: verified identity becomes a gate on sensitive-asset access. Dependencies include vendor attestation collateral, CCM/CA trust, customer policy correctness, and downstream key-release integration. [S3][S8][S12]

### Policies and security limits
- The application/node policy guide compares required application labels with available node labels; mismatches prevent certificate issuance. Build/domain approval and an active node are additional requirements in its Nitro example. **Policy is enforced at certificate issuance only in that guide: later policy changes do not revoke an issued certificate; it remains valid until expiry.** Do not describe every policy as instant runtime termination. [S12]
- The 2024 validity FAQ lists application certificates lasting **90 days**, node-agent certificates one year with weekly renewal, and CAs five years. A 2025 architecture blog calls its composite/SKR certificate short-lived without a duration. These may describe different paths; current composite-certificate lifetime and re-attestation/revocation behavior require confirmation (Q11). [S3][S18]
- SaaS 5.1 adds account-level patch grace periods. The TCB guide documents **0–365 days, default 42**, evaluated against current vendor collateral when a node attests. Administrators can flag overdue nodes and continue, or block attestation/withhold secure key release. “Trusted” is therefore policy-conditioned and can tolerate known-outdated TCB versions during a grace period: availability versus patch exposure is a real operational choice. This does not establish revocation of already-released keys. [S19][S21]
- A 5.1 patch updated CA packages/node agents/converter images for an intermediate-CA compromise, illustrating ongoing lifecycle maintenance obligations. [S20]

## Compatibility and deployment choice
The product page names **Intel TDX and AMD SEV-SNP CPUs; NVIDIA Hopper and Blackwell GPUs**. Broader documentation includes SGX/EDP, AWS Nitro and Azure confidential workloads. These are supported paths, not evidence that all combinations work. The 5.1 release limits GPU attestation to **single Hopper GPU instances or multiple Blackwell GPU instances** for TDX/SEV-SNP applications. [S2][S8][S10][S19]

**SaaS and on-premises are not feature-identical.** The October 2026 matrix supports CVMs (including TDX/SEV-SNP), EDP, groups, approvals, audit logging and metering in both. It marks several SaaS features—including Enclave OS converter paths, CoCo, ACI, datasets, registry, scripts/connectors and compute-cluster workflow execution—as unavailable or future on-prem features. On-prem workflow/application configuration support is CVM-specific. [S10]

**Documentation inconsistency:** the matrix marks on-prem collaboration groups as future, but the same-period 5.1 release announces collaboration groups/workflows for TDX/SEV-SNP CVM secure model distribution. The release likely describes a narrower exception, but exact supported combinations need confirmation (Q8). “On-prem available” does not mean full SaaS parity. [S10][S19]

Fortanix claims existing applications can run without rewrites/recompilation and VM/container integration needs no refactoring. The quickstart nevertheless requires build conversion/approval, node enrollment, platform/account setup and configuration. Separate **no code rewrite** from **no integration work**. No universal compatibility test, workload benchmark or measured implementation effort was found. [S3][S4][S11]

## Customer evidence and outcomes
**Anonymous global pharmaceutical company — explicitly CCM.** Vendor case: duplicated patient-data silos, inconsistent encryption, decentralized controls and weak monitoring led to enclave-based exchange, unified encryption/KMS workflows and controlled collaboration. It claims privacy-preserving sharing enables monetization/partnerships. Faster R&D, better services and patient outcomes are primarily potential downstream benefits, not quantified measured results. The prose does not name the customer; asset filenames do not establish identity. [S5]

**BeeKeeperAI — broader confidential-computing/DSM example.** Healthcare algorithm developers need diverse representative data to demonstrate clinical generalizability; stewards hesitate to share because of legal/ethical obligations and breach risks. The account describes keeping data in the steward's cloud, verifying consuming applications with SGX attestation, and terminating TLS inside the enclave while protecting algorithm IP. It grounds the collaboration problem and trusted-data-path design, but does not isolate CCM or quantify results. Its “minutes” and “no development or integration costs” language is a vendor claim, not a general guarantee. [S17]

**Xeureka:** CTO endorsement credits Fortanix/NVIDIA confidential computing for sensitive pharmaceutical R&D and accuracy improvement, without a figure or CCM-specific attribution. **NEC:** homepage endorsement supports application-team interest, but the linked case is a video landing page with little HTML detail; video was not processed. [S1][S2][S13]

Overall: useful vendor-published qualitative evidence, not independent validation of current CPU/GPU CCM performance, ROI or compliance.

## Why choose it, alternatives, and tradeoffs
**Stated reasons to choose:** common management across supported platforms; CPU/GPU composite verification; certificate/policy-based access to sensitive assets; reuse of existing applications; orchestration and auditability. Older CCM 3.0 material describes drag-and-drop application/dataset workflows and runtime configuration reuse; current availability must follow deployment-specific docs. [S2][S3][S10][S15]

**Inferred alternatives:** keep conventional encryption/TLS and trust infrastructure operators; build on separate cloud/hardware attestation and management services; or use another privacy-preserving collaboration approach. Fortanix argues it avoids complexity/performance penalties of alternative privacy methods, but provides no comparison sufficient to establish a win over a named competitor or cryptographic approach. [S3][S15]

**Tradeoffs to evaluate:** hardware/platform and GPU topology; SaaS/on-prem coverage; agents/build/CA/key-release integration; attestation-service/network dependencies; policy freshness and patch-grace choices; maintenance and commercial cost. These are grounded architectural considerations, not measured competitive disadvantages. [S8][S10][S11][S12][S19][S20][S21]

## Company context and claim discipline
Fortanix promotes a unified data/AI security platform and says confidential computing has underpinned its work since 2016. It claims 100+ security patents and 30+ top-conference papers. CCM connects runtime-security expertise to confidential AI and key-management services. Company-wide Key Insight/post-quantum, air-gap, HA and certification claims should not automatically be copied into a CCM configuration description. [S1][S2][S3]

Statements such as data/models “never exposed,” eliminating insider threats, and hardware isolation “satisfying” GDPR/HIPAA are marketing claims. The documented architecture supports a narrower explanation: approved, attested execution and policy-gated credentials reduce specified infrastructure-access risks under hardware, software, trust and operational conditions. This is not proof against every attack or automatic legal compliance. [S2][S3][S12][S21]

## Remaining interview-worthy uncertainty
- **Q4 — Buying group:** who champions, funds, approves and owns CCM/DSM integration versus the AI project; how security, infrastructure, data/model owners and procurement divide responsibility.

  **Working answer — inference, medium confidence:** The likely champion is a security architect or platform/confidential-computing lead working with the application or AI owner. A CISO/security executive is a plausible budget sponsor when reducing privileged-access risk drives the purchase; a CTO, engineering/AI leader or business-unit owner is more plausible when CCM enables a blocked deployment or commercial project. Security likely defines acceptable trust and key-access policies; infrastructure owns hardware, node agents, deployment and upgrades; application/model teams own builds and application integration; data stewards approve permitted data use; procurement/legal handle commercial approval. This division follows the documented workflow, rather than observed Fortanix buying histories. [S7][S8][S11][S12][S17]

  **Likely evaluation sequence — inference:** A sensitive workload encounters a trust or data-access blocker → security and application owners define requirements → platform engineers check compatibility and run a proof of concept → security/operations approve the design → the sponsor and procurement approve total cost. The approval chain will vary by customer. For research, treat technical champion and economic buyer as potentially different people.
- **Q8 — Commercial/production terms:** paid cost/licensing, mandatory bundles or supported alternative KMS integration, support/SLA and production versus early-access entitlements; exact on-prem collaboration scope where docs disagree.

  **Working answer — inference, low confidence on packaging:** Use a sales-assisted enterprise purchase, probably with recurring software/support charges, as the working commercial model. The demo/trial route and integration requirements support this assumption. Model cost as CCM charges, any required DSM/key-service charges, compatible infrastructure, implementation and ongoing operations; these need not be separate invoice items. Exact prices, billing units, minimum commitments and contract duration cannot be inferred reliably. [S2][S3][S11][S14]

  **Dependencies — inference, medium confidence:** Assume DSM is included in the Fortanix-led confidential-AI/secure-key-release architecture being researched, because the documented flow couples CCM identity with DSM key release. Do not assume every CCM use requires a DSM license. Armor is the documented account/platform context, with separate charging unknown. Another key service could technically consume a verified identity and apply authorization, but classify non-DSM integration as custom/unverified, not supported by default. [S3][S8][S11]

  **Production and on-premises scope — inference, medium confidence:** Treat readiness, support and entitlements as specific to the quoted release and deployment. Assume a production buyer will require support and operational validation; no uptime percentage or response commitment is inferred. For on-premises collaboration, use the narrower 5.1 TDX/SEV-SNP CVM secure-model-distribution path as the working scope. The feature matrix could be stale or refer to a broader capability, but the discrepancy remains unverified. Do not generalize to SaaS feature parity. [S10][S19][S20]
- **Q11 — Current runtime semantics:** composite-certificate lifetime, verification freshness/re-attestation cadence, revocation after policy or integrity changes, already-released keys, service outages and residual threat model. Public docs establish limits but do not resolve these end to end.

  **Working answer — inference, medium confidence:** Model attestation as an admission/credential-renewal check with a finite trust window. New evidence is likely needed on renewal or relevant workload/platform changes, but neither a specific interval nor continuous verification can be assumed. Treat the older 90-day application-certificate value and the composite design's unspecified short-lived certificate as different documented scopes; do not choose an exact current composite lifetime. [S3][S7][S12][S18]

  **Revocation and released keys — conservative inference:** A failed check can prevent future certificate issuance or key access. It does not necessarily stop an already-running workload or erase keys/plaintext it already holds. Ending that access may require termination, memory cleanup, rotation or application-specific controls. Which mechanisms CCM performs automatically is unverified; the label-policy guide specifically says later policy changes do not revoke an existing certificate. [S12]

  **Outages and residual trust — architectural inference:** Assume new admissions, renewals or key requests that require an unavailable service wait or fail rather than bypass verification. Existing workloads may continue while their credentials and required key material remain usable. Actual caching, retries and termination behavior are unknown. Security still depends on processor/firmware, attestation services, CCM/CA and key-service integrity, correct policies, and the trusted workload software. Application bugs or permitted outputs can still disclose information, and infrastructure operators can still interrupt service. These are working assumptions for research, not tested CCM guarantees.
